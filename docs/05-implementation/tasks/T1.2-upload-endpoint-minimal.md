## Mục tiêu

Nhận một file PDF qua `POST /api/v1/documents`, lưu tệp, tạo bản ghi `PROCESSING` và job xử lý, trả 202 kèm `documentId`.

## Bối cảnh

- Bản tối thiểu cho walking skeleton; kiểm tra đầy đủ (kích thước, kho đầy, nội dung PDF) làm ở T2.1.
- Xử lý bất đồng bộ (SDD D-07): request không chờ xử lý xong.

## Phạm vi

**Trong phạm vi**

- Endpoint upload một hoặc nhiều file (multipart)
- Kiểm tra tối thiểu: có file, đuôi/kiểu là PDF
- Lưu tệp qua `FileStorePort`
- Tạo `documents` + `processing_jobs` trong một giao dịch
- `GET /api/v1/documents` trả danh sách và trạng thái

**Ngoài phạm vi**

- Giới hạn kích thước/số trang/kho đầy (T2.1)
- Trùng file (T2.5)
- Xác thực thật (T4.1; tạm dùng người dùng dev cố định)

## Các bước thực hiện

1. Hiện thực handler theo OpenAPI (T0.2); tên file gốc chỉ lưu làm `name`, tên tệp lưu trữ là ID.
2. Với mỗi file: lưu qua `FileStorePort.put`; trong một giao dịch tạo `documents(status=PROCESSING)` và `processing_jobs(state=QUEUED)`.
3. Nếu lưu tệp thành công nhưng giao dịch lỗi: xóa tệp đã lưu (không để tệp mồ côi).
4. Trả 202 với `UploadResult[]` (mỗi file `documentId` hoặc `error`).
5. Hiện thực `GET /documents` trả các trường của `Document` (OpenAPI).
6. Phát sự kiện `document_upload_started` (thuộc tính `file_size_mb`) — có thể chỉ log nếu T4.6 chưa có.

## Tiêu chí chấp nhận

- [ ] Given người dùng dev, When gửi 1 PDF hợp lệ, Then nhận 202 kèm `documentId` và `GET /documents` hiển thị tài liệu với `status=PROCESSING`.
- [ ] Given gửi 3 PDF trong một request, When xử lý, Then có 3 kết quả riêng, 3 job riêng.
- [ ] Given gửi file `.txt`, When xử lý, Then kết quả file đó là lỗi `NOT_A_PDF` và các file khác không bị ảnh hưởng.
- [ ] Không tồn tại tệp lưu trữ nào không có bản ghi `documents` sau khi test lỗi giao dịch.

## Kiểm thử

- Integration test upload 1 file, nhiều file, file không phải PDF, lỗi CSDL giả lập.
- Contract test response khớp OpenAPI.
